# Spec：企业微信客户 AI 客服与回访助手（第一阶段）

状态：`Draft`（骨架阶段，待评审）
关联：[constitution.md](./constitution.md) · [plan.md](./plan.md) · [tasks.md](./tasks.md)

## 1. 背景

公司企业微信员工账号添加了大量客户的个人微信为外部联系人。客户会在私聊中咨询问题，公司也需要对客户进行定期回访/关怀。当前完全依赖人工，希望引入 AI：

- 客户提问由 AI 结合知识库自动回答；
- 低置信度或敏感问题转人工；
- 回访任务可由系统生成，经人工审核（或规则允许下自动）触达。

**明确不做**：不使用微信个人号协议机器人；不使用 Dify；不做加好友、拉群等主动扩列动作（该动作由人工完成）。

## 2. 角色（Actors）

| 角色 | 说明 |
|---|---|
| 客户（Customer） | 使用个人微信与企业微信员工私聊的外部联系人 |
| 企业微信员工（Agent/Staff） | 已添加客户为好友的企业微信账号使用者，AI 代其自动回复，必要时人工介入 |
| 人工客服/主管（Human Operator） | 处理转人工会话、审核回访任务、查看审计日志 |
| 知识库管理员（KB Admin） | 上传/更新知识库文档 |
| 系统管理员（Sys Admin） | 配置企业微信凭证、模型供应商、安全策略 |
| AI 服务（System） | 消息标准化、RAG 检索、生成回答、置信度判断、回访任务生成 |

## 3. 核心用例（Use Cases）

### UC-1 客户咨询 AI 自动回复
1. 客户在企业微信私聊中发送文本消息。
2. 企业微信回调网关接收事件，验签/解密后转发给消息接入层（**回调解密的具体官方细节待确认**，见 §6）。
3. 系统按 `external_userid` + 员工账号维度建立/续用会话上下文。
4. AI 服务对消息做标准化、意图/安全判断，必要时改写查询。
5. 检索 RAG 知识库，生成带引用的回答。
6. 若置信度达标且无敏感风险，通过企业微信发送接口回复客户；否则标记转人工，通知人工客服。
7. 全程记录结构化日志与审计记录（脱敏）。

**验收标准**：
- 给定命中知识库的问题，系统在无人工介入时返回带引用的回答，且响应时间在可配置超时内完成或明确超时降级。
- 给定命中黑名单关键词或低置信度的问题，系统标记为“转人工”，不自动回复业务性断言。
- 相同消息 ID 重复投递（企业微信回调重试常见现象）不会导致重复回复（幂等）。

### UC-2 知识库摄取与检索
1. 知识库管理员通过 API 上传文档（文本/Markdown 起步）。
2. 系统切分、生成 embedding、写入向量存储，并记录来源元数据。
3. 检索接口返回 Top-K 片段及相似度分数，供 AI 服务和评测使用。

**验收标准**：
- 上传文档后可在检索接口查询到对应片段；
- 每个返回片段都带来源文档 ID/标题，便于生成引用。

### UC-3 回访任务（人工/受控自动）
1. 系统按规则（如服务到期、标签、最近联系时间）生成回访任务候选。
2. 回访任务默认进入“待人工审核”队列；仅当配置显式允许且满足官方触达限制（**待确认**）时才允许自动发送。
3. 人工可批准/编辑/拒绝回访任务；批准后调用发送接口（占位，需企业微信官方能力确认）。
4. 记录每次回访的触达结果与审计。

**验收标准**：
- 回访任务创建、查询、审核（通过/拒绝）、标记发送结果的完整状态机可通过 API 驱动；
- 未经审核的任务不会被自动发送（默认关闭自动发送开关）。

### UC-4 人工接管
1. AI 判断需要转人工后，创建/更新“人工接管”状态记录，会话进入人工模式。
2. 人工模式下 AI 不再自动回复，除非人工显式将会话交还 AI。
3. 记录接管的起止时间、触发原因，供评测“转人工率”指标使用。

### UC-5 审计与评测查询
1. 系统记录每次 AI 交互的输入摘要（脱敏）、检索片段引用、回答、置信度、是否转人工。
2. 提供查询接口供运营/评测按时间、会话、员工等维度检索（**返回内容需符合最小化与授权原则**）。

## 4. 范围（In Scope，第一阶段）

- 健康检查与基础可运行骨架（FastAPI）。
- 企业微信回调验签/解密与消息规范化的**接口与占位实现**（非生产级真实对接）。
- 会话与客户映射的数据模型与内存/DB 存根。
- LLM Provider 抽象（OpenAI-compatible）与至少一个可运行的假/本地实现，便于无外网环境测试。
- Embedding/Retriever 抽象与一个可运行的内存实现（真实 pgvector 集成留待下阶段，接口先行）。
- 知识库文档上传/摄取/检索 API 草案与最小实现。
- 回访任务/人工接管的数据模型与状态机 API 草案。
- 审计日志记录与查询 API 草案。
- Docker Compose 部署骨架（app + postgres/pgvector + redis）。
- Spec Kit 文档与本仓库的 speckit 工作方式说明。

## 5. 非范围（Out of Scope，第一阶段明确不做）

- 微信个人号协议机器人接入。
- 使用 Dify 或其他一体化 AI 应用平台。
- 企业微信官方 API 的真实生产级联调（签名密钥、正式 access_token 获取、真实消息发送）——仅提供抽象接口和占位实现，标注 `TODO(confirm-with-wecom-docs)`。
- 自动无限制主动加好友/拉群/批量营销。
- 多租户、复杂权限体系（第一阶段单租户，权限模型简单占位）。
- 语音/图片/文件类消息的完整处理（仅预留消息类型字段，第一阶段只处理文本）。

## 6. 待确认事项（Open Questions / TODO(confirm-with-wecom-docs)）

1. 企业微信客户联系消息回调的加解密算法与验签细节的最新版本要求（AES/CBC 参数、Token 有效期等）需对照官方最新文档逐项确认。
2. “自动回复”允许的会话时间窗口（如 48 小时规则）在当前企业主体、应用类型下的实际生效范围。
3. 主动发送（回访/关怀）消息的频率限制、消息类型限制、是否需要客户预先同意/开启会话存档。
4. 客户会话内容合规存档能力是否已开通，是否需要客户授权提示。
5. 客户身份与企业微信 `external_userid`、员工 `userid` 的唯一性和跨企业场景下的映射规则。
6. 具体可用的企业微信 API 权限集合（客户联系 API vs 客服消息 API）取决于当前企业资质与应用配置，需要在真实对接前用测试企业验证。

## 7. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 企业微信官方权限/限制与预期不符 | 回访/自动回复功能可能受限 | 先用测试企业验证，接口层保持可替换，功能开关默认保守 |
| 模型幻觉/错误回答 | 客户体验/合规风险 | 强制引用、低置信度转人工、离线评测门槛 |
| 客户隐私泄露 | 合规风险 | 默认脱敏、最小化存储、访问审计 |
| 重复消息/网络重试导致重复回复 | 打扰客户 | 幂等键 + 去重存储 |
| 依赖模型供应商变化 | 成本/可用性 | OpenAI-compatible 抽象层，供应商可替换 |
