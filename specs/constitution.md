# 项目宪法（Constitution）

> Spec Kit 文档层级：`constitution.md`（原则）→ `spec.md`（做什么/为什么）→ `plan.md`（怎么做/技术方案）→ `tasks.md`（可执行任务拆解）。
> 本文件定义项目不可轻易违反的基本原则，后续所有 spec/plan/tasks 都必须与本文件保持一致；如需修改原则，需在 PR 中显式说明理由。

## 1. 项目使命

为企业微信客户（外部联系人为客户个人微信，企业侧为企业微信员工账号）提供：

1. AI 自动问答与 RAG 知识库检索；
2. 受控的人工/自动客户回访；
3. 完整的审计、日志与可观测能力，保障合规与可追责。

## 2. 硬性原则（Non-negotiable）

1. **不接入微信个人号协议机器人**（不使用 Wechaty/Puppet/Hook/模拟登录等灰色方案）。所有与“微信”的交互均通过企业微信官方开放能力的抽象接口进行；未验证的官方能力一律标记为 `TODO(confirm-with-wecom-docs)`，不得臆造已确认能力。
2. **不使用 Dify** 或其他重量级一体化 AI 平台；不引入不必要的微服务，第一阶段坚持**模块化单体（modular monolith）**。
3. **AI 优先做 RAG 问答，Agent 能力仅保留受控扩展点**：模型不允许在没有显式白名单工具与人工/规则审核的情况下调用外部系统或发起主动动作。
4. **低置信度/敏感问题必须能转人工**，无法满足置信度或存在合规风险时禁止让模型编造答案。
5. **主动触达（回访/关怀消息）默认受控**：必须经过频率限制、会话窗口/权限校验和（可配置的）人工审核开关，不做无限制批量触达。
6. **隐私与数据最小化**：默认不留存未经业务需要的客户隐私字段；日志脱敏是默认行为而非可选项；仅在明确合规授权后才启用会话内容存档。
7. **可私有化部署**：技术栈必须能够在客户自有基础设施（Docker Compose 起步）完整运行，不强依赖外部 SaaS（模型 API 除外，且需可替换）。
8. **一切对外部（企业微信官方）能力的假设都必须在文档中标注确认状态**（已确认 / 待确认 / 已知限制），不得在代码注释或 API 文档中暗示某项官方能力已经过验证，除非有官方文档引用。

## 3. 架构原则

- 分层清晰：适配器层（企业微信）→ 应用服务层（会话/AI/回访/人工接管）→ 领域层（知识库、评测、审计）→ 基础设施层（DB/Redis/队列/LLM/向量检索）。
- 所有外部依赖（LLM、embedding、消息发送、消息回调）通过接口/协议（Python `Protocol` 或抽象基类）隔离，便于替换和测试。
- 幂等优先：所有对外部系统有副作用的操作（发送消息、写入审计）必须设计幂等键。
- 超时与重试：所有网络调用需设置超时，重试需有上限与退避策略，不允许无限重试。

## 4. 变更流程

1. 任何范围变更先更新 `specs/spec.md` 的“范围/非范围”。
2. 技术选型变更先更新 `specs/plan.md` 并说明替代方案对比。
3. 任务拆解变化更新 `specs/tasks.md`，保持任务状态可追踪。
4. 若变更违反本文件任一原则，必须在 PR 描述中显式说明豁免理由，并经评审确认。

## 5. 完成定义（Definition of Done，适用于本阶段所有任务）

- 类型标注齐全，关键路径有单元测试；
- 无网络访问的测试可在 CI/本地无外部依赖运行；
- 涉及外部官方能力的地方均有 `TODO(confirm-with-wecom-docs)` 或引用标注；
- 无敏感配置写入代码库；
- README/相关文档同步更新。
