# RAG / Agent 核心链路

## 1. 总体流程

```text
原始消息(企业微信)
    │  wecom 适配器：验签/解密/规范化
    ▼
NormalizedEvent（发送者、内容、msg_id、时间戳）
    │  幂等去重（msg_id）
    ▼
会话上下文加载/创建（Conversation + 最近 N 条历史）
    │
    ▼
意图/安全判断（关键词黑名单 + 可选模型判断）
    │  命中敏感 → 直接转人工，跳过后续生成
    ▼
查询改写（可选，第一阶段不启用，接口预留 QueryRewriter）
    │
    ▼
检索（Retriever.search，向量检索；未来可加关键词混合检索）
    │
    ▼
（可选）Rerank（第一阶段不启用，接口预留 Reranker）
    │
    ▼
Prompt 组装（系统提示 + 会话历史 + 检索片段 + 回答约束）
    │
    ▼
LLM 生成（LLMProvider.generate，超时/重试受控）
    │
    ▼
置信度判断（基于检索分数 + 模型自评/规则）
    │  低于阈值 → handoff_required=true
    ▼
回答 + 引用 组装 → 返回 / 转人工
    │
    ▼
审计日志记录（脱敏）
```

## 2. 各阶段说明

### 2.1 消息标准化
- 输入：企业微信原始事件（占位）。
- 输出：`NormalizedEvent`（`msg_id`, `from_external_userid`, `to_staff_userid`, `msg_type`, `content`, `timestamp`）。
- 第一阶段仅处理 `text` 类型，其余类型标记为 `unsupported` 并直接转人工。

### 2.2 会话上下文
- Key：`(customer_external_userid, staff_userid)` → `conversation_id`。
- 历史消息条数与过期时间可配置（默认最近 10 条 / 30 分钟），避免无限增长的上下文。

### 2.3 意图/安全判断
- 第一阶段使用可配置关键词黑名单（如涉及退款金额纠纷、投诉、法律等）做规则判断；命中则直接 `handoff_required=true`，不进入生成流程。
- 预留接口位置支持未来接入模型分类器，但第一阶段不实现以保持简单可测。

### 2.4 查询改写（可选）
- 接口预留 `QueryRewriter.rewrite(query, history) -> str`，第一阶段使用恒等实现（不改写），避免引入额外的模型调用延迟和不确定性。

### 2.5 检索
- `Retriever.search(query, top_k)` 返回按分数排序的片段列表。
- 第一阶段实现：内存暴力余弦相似度检索（`InMemoryRetriever`），便于无数据库环境下测试；生产实现应替换为 pgvector 查询，接口保持不变。

### 2.6 Rerank（可选）
- 接口预留 `Reranker.rerank(query, chunks) -> chunks`，第一阶段使用恒等实现（不重排）。

### 2.7 回答约束
- Prompt 模板要求模型：
  1. 仅基于检索片段回答，禁止编造检索之外的事实；
  2. 无法从片段中找到答案时，明确说明并建议转人工，而不是猜测；
  3. 引用来源（`source_id`）必须包含在结构化输出中。

### 2.8 低置信度转人工
- 置信度计算（第一阶段简化）：取检索片段最高分数与是否命中黑名单的组合规则；未来可加入模型自评分数。
- 低于可配置阈值（默认 `0.35`，纯占位数值，需结合真实评测调整）时，`handoff_required=true`。

### 2.9 工具调用边界（Agent 受控扩展点）
- 第一阶段**不实现**任何工具调用；仅在 `services/ai_orchestrator.py` 中预留 `allowed_tools: list[str] = []` 的扩展点和显式白名单设计说明：
  - 任何工具调用都必须显式在配置中列出白名单函数签名；
  - 工具执行结果需要记录审计日志；
  - 模型输出的“调用工具”意图必须经过程序化校验（不能直接执行模型生成的任意代码/命令）。

### 2.10 超时/重试/幂等
- LLM 调用：超时可配置（默认 15s），失败重试至多 1 次（指数退避基数 0.5s），仍失败则转人工并返回明确错误。
- 检索调用：超时可配置（默认 5s），失败则跳过 RAG 直接转人工（避免无依据回答）。
- 幂等：以 `msg_id`（或显式 `idempotency_key`）为键，处理结果缓存（第一阶段用内存字典，生产应使用 Redis + TTL）。

## 3. 为什么第一阶段以 RAG 为主，Agent 仅做受控扩展点

- 客服场景对“可控性”和“可解释性”要求高，允许模型任意调用外部系统（下单、改价、查询 CRM 等）在没有充分的权限校验、审计和回滚机制前风险很高；
- 先把 RAG 问答链路做扎实（检索质量、置信度、转人工），再逐步开放受控的工具白名单，是更稳妥的演进路径；
- 这也与 [specs/constitution.md](../specs/constitution.md) 的硬性原则一致。
